# 模块 4：Selenium Web UI 自动化

目标：完成一个小而真实的 pytest + Selenium 项目，理解定位、等待、断言、fixture、Page Object 和失败证据。无需在本阶段学习 Selenium Grid、复杂前端框架内部原理或多浏览器云平台。

## 一、必须掌握的理论

### 1. 什么适合自动化

优先自动化：稳定、重复执行、业务关键、预期明确的流程。一次性需求、频繁改版、强依赖人工视觉判断的场景不应优先。

### 2. DOM 与元素定位

优先使用稳定且唯一的 `id`、`name`、测试专用属性；其次使用结构清晰的 CSS。XPath 可以使用，但不要写依赖层级和序号的脆弱长路径。

定位后必须确认：唯一性、可见性、可交互性、页面刷新后是否仍稳定。

### 3. 常见交互

- 输入、点击、清空、读取文本/属性。
- 下拉框、复选框、单选框。
- Alert、iframe、多个窗口或标签页。
- 滚动、悬停等特殊操作只在业务需要时使用。

### 4. 等待

- 隐式等待是全局轮询，容易让失败耗时和行为难以判断。
- 显式等待针对具体条件：元素出现、可见、可点击、文本变化、URL 变化。
- 固定 `sleep` 只能用于极少数调试或无法观察的外部等待，不能作为项目主要同步机制。

### 5. 断言

点击成功不等于业务成功。应断言用户可观察结果，例如：URL、提示文本、商品数量、订单状态、按钮状态或页面关键内容。

### 6. pytest fixture

fixture 用于统一管理浏览器创建、配置和关闭，避免每条用例重复启动逻辑。即使用例失败，也应可靠执行清理。

### 7. Page Object

Page Object 把页面定位和页面操作封装在页面类中，用例只表达业务步骤和断言。

它解决的是维护性，不是为了增加类的数量。继承只在多个页面确实共享浏览器、等待、截图等行为时使用。

### 8. 稳定性与证据

- 测试数据可重复，不依赖上次运行残留。
- 用例之间尽量独立。
- 失败时保存截图、日志和关键页面信息。
- README 写清浏览器、驱动、依赖、运行命令和已知限制。

## 二、理论验收题

1. 哪些 UI 场景适合自动化，哪些不适合？
2. 为什么定位器稳定性比“现在能点到”更重要？
3. CSS 和 XPath 应如何选择？
4. 元素存在、可见、可点击有什么区别？
5. 隐式等待、显式等待和 `sleep` 有什么区别？
6. 为什么大量使用固定 `sleep` 会导致用例慢且不稳定？
7. iframe 中的元素为什么不能直接定位？
8. 打开新窗口后为什么要切换 window handle？
9. 点击提交后应该断言什么，而不是只断言点击未报错？
10. fixture 如何保证浏览器最终关闭？
11. Page Object 解决什么问题？
12. Page Object 中应该放断言吗？什么时候可以例外？
13. 为什么用例之间不应该依赖执行顺序？
14. UI 自动化失败时应保留哪些证据？
15. 什么是数据驱动？什么情况下会导致用例难读？
16. 为什么不能自动化所有功能测试？
17. 父类/子类在 Page Object 中可能如何使用？
18. 自动化用例本身出现偶发失败时，应该怎么定位？

## 三、验收项目：Web UI 自动化小项目

新建独立仓库 `web-ui-test-framework`，固定使用 Python + Selenium + pytest。

最低结构：

```text
web-ui-test-framework/
├── pages/
├── tests/
├── data/
├── utils/
├── conftest.py
├── pytest.ini
├── requirements.txt
└── README.md
```

最低用例：

1. 正常登录。
2. 错误密码登录。
3. 商品筛选或排序。
4. 加入购物车并验证数量/内容。
5. 完成结算或提交表单。
6. 至少一条边界或异常用例。

技术验收：

- 使用显式等待，不以大量固定 `sleep` 维持运行。
- 至少两个 Page Object。
- 浏览器生命周期由 fixture 管理。
- 失败时自动截图。
- 测试结果可重复，连续运行两次结果一致。
- README 从全新环境可以照做运行。

讲解验收：能在 3 分钟内说明项目目标、结构、定位策略、等待策略、Page Object、失败截图和一个实际排错过程。
