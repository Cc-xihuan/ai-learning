# 参考答案与评分要点

使用规则：必须先口述和书面作答，再查看本文件。这里给的是评分锚点，不是唯一措辞。

## Linux

- 路径题：必须正确区分根目录、主目录、当前目录、父目录和绝对/相对路径。
- 日志题：应说出 `grep`、行号、上下文、时间/request_id 等关联证据，不能只说“搜 ERROR”。
- 服务题：至少包含进程 → 端口 → HTTP → 日志；能补充 DNS/网络更好。
- 权限题：能读懂所有者/组/其他用户，知道 `777` 会扩大风险。
- 删除、强制杀进程等高风险操作必须先确认目标和影响。

## 测试理论

- 冒烟用于判断版本是否值得继续测；回归用于验证修改及关联影响。
- 等价类解决代表性，边界值关注临界点，判定表处理条件组合，场景法处理业务路径，状态迁移处理状态变化。
- 严重程度是影响，优先级是修复顺序，两者相关但不等同。
- Bug 报告必须可复现、有预期/实际和环境证据。
- 上线判断必须结合核心链路、严重缺陷、覆盖/未测、遗留风险和回滚能力。

## HTTP/接口

- 401 是未完成有效认证，403 是身份已知但无权限。
- 幂等关注最终服务器状态，不是响应文本是否完全一样。
- Cookie 常由客户端保存；Session 状态通常在服务端；Token 常放 Authorization Header。
- 接口断言至少覆盖协议、结构和业务，关键场景增加数据库或副作用验证。
- 前后端定位必须使用请求、响应、日志和数据证据；不能把所有 4xx 都归后端。
- `requests.Session()` 自动保持 Cookie，但 Token 需要写入 Cookie 或 Header。

## Selenium

- 稳定定位器优先；长层级 XPath 和位置序号通常脆弱。
- 显式等待等待可观察条件；大量固定 sleep 会导致慢、偶发和难定位。
- Page Object 封装页面元素与操作，用例表达业务；不应为了形式堆类。
- 用例失败应保留截图、日志、URL、页面状态和异常堆栈。

## pytest/项目

- fixture 用于可复用准备/清理；scope 必须符合资源生命周期和隔离要求。
- 数据驱动适合相同逻辑的多组数据，不适合把完全不同业务塞进同一用例。
- 关联值必须解析、校验并提供清楚失败信息。
- 数据库测试需隔离或清理数据；模拟数据库必须明确边界。
- README 应包含目标、结构、安装、运行、结果和限制。

## 场景题评分通用标准

每道场景题按以下维度检查：

1. 是否先澄清需求，而不是立即罗列用例。
2. 是否覆盖正常、异常、边界、权限、状态和数据。
3. 是否考虑依赖失败、重复提交和可观察证据。
4. 是否按业务风险安排优先级。
5. 是否给出清晰预期，而不只写操作步骤。

常见扣分：只列页面字段；只测正常流程；用例数量很多但重复；没有前置条件和测试数据；把性能、安全等词语罗列出来但说不出如何验证。
