# 模块 3：HTTP 与接口测试

目标：能看懂请求与响应，使用浏览器开发者工具、curl 或 Postman 复现接口，设计正常/异常用例并做初步定位。

## 一、必须掌握的理论

### 1. HTTP 请求与响应

请求主要包含：方法、URL、查询参数、Header、Cookie、Body。

响应主要包含：状态码、Header、Cookie、Body 和耗时。

URL 常见结构：

```text
https://api.example.com:443/orders/1001?detail=true
协议       主机             端口 路径          查询参数
```

### 2. 常见方法

- GET：读取资源，通常不应改变服务器状态。
- POST：创建资源或执行动作，重复调用可能产生重复结果。
- PUT：整体替换资源，通常具有幂等语义。
- PATCH：部分更新资源。
- DELETE：删除资源。

幂等表示同一请求执行一次或多次，对服务器最终状态的影响相同；不等于每次响应内容一定完全一致。

### 3. 常见状态码

- 200 成功；201 创建成功；204 成功但无响应体。
- 400 请求格式/参数错误；401 未认证；403 已认证但无权限；404 资源不存在；409 冲突；429 请求过多。
- 500 服务内部错误；502 网关得到无效响应；503 服务不可用；504 网关等待上游超时。

状态码只是线索。4xx 不一定都是前端 Bug，5xx 也需要结合网关、服务和依赖日志定位。

### 4. Header、Cookie、Session、Token

- `Content-Type` 描述发送的数据格式。
- `Accept` 描述客户端希望接收的格式。
- Cookie 通常由浏览器保存并在后续请求中携带。
- Session 常指服务端保存的会话状态，客户端通过 Session ID 关联。
- Token 常放在 `Authorization` Header 中，例如 Bearer Token。

`requests.Session()` 会自动保持 Cookie；Token 只有被写入 Cookie 或 Session Header 后才会自动携带。

### 5. JSON 与断言

接口测试不能只断言状态码。常见断言层次：

1. 协议层：状态码、Content-Type、耗时。
2. 结构层：字段存在、类型正确、Schema 符合。
3. 业务层：金额、状态、权限、计算结果正确。
4. 数据层：数据库或后续查询结果一致。
5. 副作用：重复请求、消息、库存、日志等是否符合预期。

### 6. 接口测试设计

至少覆盖：

- 正常参数和核心业务流。
- 缺失、空值、错误类型、超长、越界、非法枚举。
- 未认证、Token 过期、越权访问。
- 资源不存在、重复提交、并发或幂等。
- 上下游依赖异常、超时和错误返回。
- 接口关联：登录获取 Token、创建资源得到 ID、查询/更新/删除该 ID。

### 7. 初步排查路径

页面操作失败时：

1. Network 中请求是否发出。
2. URL、方法、参数、Header 是否正确。
3. 状态码、响应体和耗时是什么。
4. 同一请求能否用 curl/Postman 复现。
5. 请求 ID、时间和账号对应的服务日志是什么。
6. 数据库或下游服务状态是否正确。

## 二、理论验收题

1. HTTP 请求和响应分别由哪些主要部分组成？
2. Path 参数和 Query 参数有什么区别？
3. GET、POST、PUT、PATCH、DELETE 分别常用于什么？
4. 什么是幂等？POST 一定不幂等吗？
5. 200、201、204 有什么区别？
6. 400、401、403、404、409、429 分别表示什么？
7. 502、503、504 的排查方向有什么不同？
8. `Content-Type` 和 `Accept` 有什么区别？
9. Cookie、Session、Token 之间有什么关系？
10. 401 与 403 的区别是什么？
11. 为什么只断言状态码不够？
12. JSON 中对象、数组、字符串、数字、布尔和 null 如何表示？
13. 登录接口应该覆盖哪些异常场景？
14. 如何测试越权访问？
15. 如何测试接口重复提交？
16. 接口关联是什么？举一个创建后查询的例子。
17. 页面提示“保存失败”，你如何判断是前端还是后端？
18. Postman 能成功而页面失败，可能有哪些原因？
19. 页面和 Postman 都失败，下一步需要什么证据？
20. `requests.Session()` 会自动记住 Token 吗？
21. 公开模拟 API 的 POST 不落库时，项目 README 应如何说明？
22. 接口响应很慢但最终 200，是否算问题？如何判断？

## 三、实操验收

选择一个公开练习 API 或后续提供的本地 API，完成：

1. GET 列表、GET 详情、POST 创建、错误资源四类请求。
2. 保存环境变量 `base_url`，不要把地址散落在每个请求中。
3. 为请求编写状态码、字段、类型和业务值断言。
4. 至少设计 8 条异常或边界测试。
5. 保存一次失败请求的完整证据：方法、URL、参数、状态码、响应、时间。
6. 使用 curl 重放其中一个请求，并说明与 Postman 的对应关系。

## 四、验收项目：接口测试交付包

在 `ai-learning/portfolio/api-manual-test/` 中完成：

- `api_inventory.md`：接口清单、方法、路径、认证和用途。
- `api_test_cases.md`：至少 20 条接口用例。
- `postman_collection.json`：可导入执行的集合。
- `environment.example.json`：不包含真实密码和 Token。
- `bug_report.md`：一份有请求/响应证据的接口 Bug 报告。
- `test_summary.md`：范围、结果、风险和限制。

通过标准：集合可在新环境运行；密钥不进入 Git；断言不仅检查 200；能解释至少一次接口关联和一次失败定位。
