# 模块 5：`api-test-framework` V2

目标：在现有真实仓库上增加能被测试实际使用的能力，让项目从“请求练习”升级为可讲解的初级接口自动化项目。

## 一、必须掌握的理论

### 1. 框架分层

- 配置层：环境、基础 URL、超时等。
- 数据层：测试输入和预期。
- 工具层：请求、日志、断言、数据读取。
- 用例层：业务场景和验证。
- 报告/持续集成：输出结果和自动执行。

分层的目标是减少重复并提高可维护性，不是目录越多越好。

### 2. fixture 与前后置

fixture 负责共享准备和清理，例如 API Session、测试数据、数据库连接。scope 应根据资源生命周期选择，不能为了少写代码让所有用例共享会相互污染的状态。

### 3. 会话与鉴权

- Cookie 会话可由 `requests.Session()` 自动保持。
- Bearer Token 通常要显式写入 Session Header。
- 密钥、密码、Token 不进入代码和 Git；仓库只提供 `.env.example` 或示例配置。

### 4. 接口关联

上一步响应中的 ID、Token 等作为下一步输入。关联值应从响应中解析并进行存在性/类型检查，失败时给出清楚信息。

### 5. 断言策略

公共断言可以减少重复，但不能把所有业务判断写成一个巨型万能函数。断言失败信息要说明预期、实际和关键上下文。

### 6. 数据库校验

接口返回成功后，用数据库验证关键副作用；测试数据必须可回收或隔离。公开模拟 API 不落库时，可使用本地 SQLite 构造可重复的校验场景，并在 README 明确这不是远程 API 的真实数据库。

### 7. 报告与 CI

报告用于快速看到失败用例、步骤和错误信息。CI 用于在 push/PR 时自动安装依赖并运行测试。CI 通过不代表业务一定正确，只证明当前自动化检查通过。

## 二、理论验收题

1. 为什么要把配置、数据、工具和用例分开？
2. 什么情况下不应该继续抽象公共函数？
3. fixture 的 function、class、module、session scope 有什么差异？
4. API Session 为什么适合用 fixture 管理？
5. Cookie 与 Bearer Token 的保存方式有什么区别？
6. 为什么 Token 不能硬编码进仓库？
7. 什么是接口关联？关联值提取失败时应如何处理？
8. 为什么不能只写一个“万能断言函数”？
9. 好的断言失败信息应该包含什么？
10. 数据驱动适合什么场景？什么时候会让用例难以理解？
11. 数据库校验解决什么问题？
12. 测试产生的数据如何避免污染下次运行？
13. Mock API 的 POST 不落库时，为什么不能宣称实现了真实数据库校验？
14. HTML 报告与 Allure 分别能解决什么问题？
15. GitHub Actions 的最小工作流包括什么？
16. CI 偶发失败时应该保存哪些信息？
17. 如何证明一个新工具模块真的被项目使用了？
18. 项目 README 的“已知限制”为什么重要？

## 三、V2 必做改造

按顺序完成，每完成一项先保持全部测试通过：

1. 使用 fixture 提供统一的 `requests.Session` 和基础配置。
2. 增加一个至少两步的接口关联场景。
3. 增加鉴权示例：Token 写入 Header；没有真实鉴权服务时使用本地可控练习服务。
4. 增加 SQLite 校验场景，并明确其教学边界。
5. 为新增功能补充正常、异常和边界测试。
6. 改进失败信息和日志，敏感字段脱敏。
7. 更新 README：架构、运行、结果、限制和排错说明。

加分但不作为 70% 硬门槛：Allure、GitHub Actions、JSON Schema、重试策略。不得使用重试掩盖真实不稳定问题。

## 四、项目验收

- 原有 8 条测试不退化。
- 每个新增模块至少被一个真实测试调用。
- 连续运行两次结果一致。
- 新环境按 README 可以安装并运行。
- 仓库无真实 Token、密码、密钥和隐私数据。
- 能现场指出公开模拟 API 的限制，不把模拟结果包装成真实商城项目。
- 3 分钟项目讲解和 5 分钟追问均能完成。

推荐追问题：

1. 为什么选 pytest 而不是 unittest？
2. YAML 数据驱动带来了什么好处和问题？
3. 请求封装和业务用例的边界在哪里？
4. 如果某接口偶发 500，你如何定位？
5. 如果让你接入多环境和真实鉴权，你会怎么改？
