## 1. 功能测试与用例设计

**理论。** 需求给出允许和禁止的行为，测试用例把它变成可执行的操作与可观察的预期。等价类把预期相同的输入分组，边界值测分界线两侧，状态迁移检查某状态下操作能否发生，场景法把多个操作串起来。需求漏写异常时，先记录需要确认的问题。

**例子。** 本地订单接口限制单条明细数量为 1 到 99，且实际库存必须够。可以用 `0、1、99、100` 检查入参边界。验证 `99` 的上边界时要准备至少 99 件库存，或明确单独观察入参验证。否则被库存拦截时，仍无法证明 99 件可以正常创建。库存边界另用库存数和库存数加一检验。

| 场景 | 操作 | 预期与证据 |
|---|---|---|
| 正常下单 | 已登录，库存足够，数量为 1 | 返回 201，订单号存在，数量与金额正确，订单落库 |
| 数量越界 | 保留登录和商品条件，只把数量改为 0 | 本项目返回 422，数据库没有本次订单 |
| 重复下单 | 同一用户、同一请求体和同一个幂等键连续提交两次 | 首次 201，第二次 200，两次订单号相同，库里只有一笔 |

**验收题。** 给一个“预订金额超过 500 元才需审批”的假设需求，写三个边界输入和各自预期。再写一个权限用例。补充两个需要向产品确认的问题。讲清前置条件、操作和预期，每条都能执行。

## 2. HTTP 与接口测试

**理论。** 一次请求包括方法、URL、Header 和可能存在的请求体。登录接口给出 Token，后续通过 `Authorization: Bearer …` 携带身份。响应先看 HTTP 状态码，再看业务字段，必要时查数据库副作用。超时表示客户端没及时拿到结果，服务端可能已经执行，重试时要验证同一业务动作只发生一次。

| 状态码 | 在练习项目里的含义 |
|---|---|
| 200 / 201 | 成功 / 创建成功。同键重放在此项目返回 200 |
| 401 / 403 | 身份未通过验证 / 当前身份没有操作权限 |
| 404 | 查询的订单或商品不存在 |
| 409 | 当前库存或状态与请求冲突 |
| 422 | 请求参数不符合校验规则，例如数量为 0 |

**动手。** 打开 PowerShell 7（`pwsh`）。第一个窗口启动本地服务，使用单独的练习数据库。该窗口保持运行。

```powershell
Set-Location 'D:\Dev\Projects\enterprise-order-testing'
$env:DATABASE_URL = 'sqlite:///./qa_lab_order.db'
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8765
```

第二个 PowerShell 7 窗口发请求。登录用的是项目自带的演示账号。`ConvertTo-Json` 把 PowerShell 对象转成请求所需的 JSON。

```powershell
Set-Location 'D:\Dev\Projects\enterprise-order-testing'
$base = 'http://127.0.0.1:8765'
$health = Invoke-RestMethod "$base/health"
if ($health.status -ne 'UP') { throw '本地练习服务未就绪' }

$loginBody = @{ username = 'qa_user'; password = 'Qa123456!' } | ConvertTo-Json
$login = Invoke-RestMethod "$base/api/auth/login" -Method Post `
  -ContentType 'application/json' -Body $loginBody

$key = 'qa-' + [guid]::NewGuid().ToString('N')
$headers = @{ Authorization = "Bearer $($login.access_token)"; 'Idempotency-Key' = $key }
$body = @{ items = @(@{ product_id = 1; quantity = 1 }) } | ConvertTo-Json -Depth 4

$first = Invoke-RestMethod "$base/api/orders" -Method Post -Headers $headers `
  -ContentType 'application/json' -Body $body -StatusCodeVariable firstCode
$second = Invoke-RestMethod "$base/api/orders" -Method Post -Headers $headers `
  -ContentType 'application/json' -Body $body -StatusCodeVariable secondCode

[pscustomobject]@{
  FirstStatus = $firstCode
  SecondStatus = $secondCode
  FirstOrderNo = $first.order_no
  SecondOrderNo = $second.order_no
  UserId = $first.user_id
  Total = $first.total_amount
} | Format-List
```

`$key` 每轮生成一次，同一轮的两次请求共用它。预期首次是 201、重放是 200，两次订单号相同。这个场景验证的是串行重试，并发提交需要单独设计。看到 409 时先读 `detail`，判断是否库存不够。可打开 [本机接口文档](http://127.0.0.1:8765/docs) 查看参数，也可以在 Postman 用相同的 URL、Header 和 JSON 重做。练习记录只保留状态码、订单号和必要字段，去掉 Token。

**验收题。** 解释同一个订单号能证明什么。然后只改一个条件做对照，比如去掉 Token，或用新幂等键将数量改为 0。提交前先写预期，再看真实响应。PowerShell 7 用 `-SkipHttpErrorCheck -StatusCodeVariable actualCode` 读取非 2xx 的响应体和状态码。

## 3. SQL 查库

**理论。** `orders.id` 是订单主键，`order_items.order_id` 是明细指向订单的外键。按订单号用 `WHERE` 查订单，按外键 `JOIN` 明细。查重时按“用户 ID + 幂等键”过滤，因为这个项目的幂等范围是同一用户。对明细表做 JOIN 后，一笔订单可能出现多行，直接数 JOIN 后的行数会把明细数当成订单数。

**动手。** 在刚才的第二个窗口继续执行。Python 这里只负责以只读方式打开 SQLite 并执行 SQL。`?` 是参数占位，具体值由刚才的请求结果传入。

```powershell
@'
import sqlite3
import sys

user_id, key, order_no = sys.argv[1:]
with sqlite3.connect("file:qa_lab_order.db?mode=ro", uri=True) as db:
    row = db.execute(
        "SELECT COUNT(*) FROM orders WHERE user_id = ? AND idempotency_key = ?",
        (int(user_id), key),
    ).fetchone()
    print("matching_orders =", row[0])

    rows = db.execute(
        """
        SELECT o.order_no, o.status, o.total_amount, i.quantity, i.unit_price
        FROM orders AS o
        JOIN order_items AS i ON i.order_id = o.id
        WHERE o.order_no = ?
        """,
        (order_no,),
    ).fetchall()
    print("order_details =", rows)
'@ | .\.venv\Scripts\python.exe - $first.user_id $key $first.order_no
```

期望 `matching_orders = 1`，订单状态为 `CREATED`，金额和数量与接口返回一致。练完在服务窗口按 Ctrl+C 停止服务。

**验收题。** 只给你订单号，独立手写一条 SQL 查状态、金额和明细数量。再解释为什么两次 HTTP 响应看起来都成功，仍然要核对实际订单数。

## 4. 缺陷、复测与回归

**理论。** 缺陷需要能复现。记录测试环境和版本、前置、步骤、预期、实际、证据和影响。严重度看影响，例如是否资损；优先级看处理顺序。修复后用原始步骤确认缺陷是否消失，再回归可能受影响的已有流程。冒烟用少数核心场景快速判断当前版本是否值得继续测。

**动手。** 用你实测的结果写一条记录。实际符合预期就标通过。如果真的出现两笔，缺陷标题可写「同一账号同键重放生成不同订单号」。证据给两次请求时间、两次状态码、两个订单号以及查库结果。定位时先用订单号或请求 ID 把页面现象和接口关联，再查日志与数据；把“观察到了什么”和“怀疑哪里有问题”分开写。

**验收题。** 页面提示支付失败，但订单查询显示已支付。说出你要拿哪三类证据，以及复测时除了原始步骤还会回归什么。未知的支付或出票规则写为待确认。

## 5. pytest 项目追问

**理论。** 用例代码通常按准备数据、执行请求、断言结果写。参数化用于同一套动作验证多组输入，fixture 用于提供需要复用的前置条件，例如测试客户端或登录头。断言要能说明业务风险，例如“同键返回相同订单号”对应重复建单风险。
